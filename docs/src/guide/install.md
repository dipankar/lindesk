# Installation

Install the `lindesk` package. Telemetry is an optional add-on in its own package:

| Package | Contains | Size |
|---|---|---|
| `lindesk` (core) | `lindeskd`, `lindesk-session`, `lindeskctl`, `lindesk-mcp`, `lindesk-bench`, units, profiles, rules, desktop integration | small: no DuckDB, no Vortex/Arrow linked |
| `lindesk-telemetry` (optional, depends on `lindesk`) | `lindesk-data` (DuckDB: query, export/import, compaction, retention), the `telemetry` plugin (`lindesk-telemetry-sink`, the Vortex lake writer) with its two manifests in `/usr/lib/lindesk/plugins/`, the `lindesk-compact` timers, `lindesk-data(1)` | large (bundled DuckDB) |

lindesk works the same without telemetry: it governs, explains and can be tuned. The
optional telemetry adds the history: `lindeskctl query`, `data`, `simulate`, the telemetry evidence in the MCP
`recommendations`, and storing `lindesk-bench` runs. Without it those commands say
`telemetry isn't installed: sudo apt install lindesk-telemetry (or ./packaging/install.sh
--with-telemetry)` and `lindeskctl doctor` / `status` show `telemetry: not installed
(optional)` as information, not as a problem. `lindesk-telemetry` is never installed
automatically (the core only `Suggests` it).

## Packages

```console
$ sudo apt install ./lindesk_*_amd64.deb            # Debian, Ubuntu, Pop!_OS
$ sudo dnf install ./lindesk-0*.rpm                 # Fedora
$ makepkg -si                                       # Arch (packaging/aur; also builds lindesk-telemetry)

# Optional: telemetry & DuckDB queries
$ sudo apt install ./lindesk-telemetry_*_amd64.deb  # or ./lindesk-telemetry-*.rpm, pacman -U lindesk-telemetry-*
```

Installing `lindesk-telemetry` needs no configuration: its post-install reloads `lindeskd`
(`systemctl reload-or-restart lindeskd`, a SIGHUP that loads new plugins without undoing
anything) and every running `lindesk-session`, which discover the `telemetry` plugin and
start recording. A session agent the package could not reach picks it up at its next start
or `systemctl --user reload lindesk-session`. Removing it restarts `lindeskd` without the
plugin; session agents drop it at their next start (until then the already-running writer
keeps recording). Nothing errors in between: a missing plugin is simply not loaded.

## Anything else

```console
$ ./packaging/install.sh                       # checks, builds and installs the core, enables and starts it
$ ./packaging/install.sh --with-telemetry      # also the optional telemetry (builds DuckDB: slow, large)
$ ./packaging/install.sh --uninstall
```

A plain re-run (an upgrade) keeps whatever is installed. `--with-telemetry` adds telemetry
and reloads the daemons; `--without-telemetry` removes it again and restarts `lindeskd`.

`install.sh` also installs shell completions and man pages generated by `lindeskctl`
(`lindeskctl completions <shell>`, `lindeskctl man <dir>`).

## Start it

Packages enable both services (and, with `lindesk-telemetry`, the `lindesk-compact`
timers). To do it by hand:

```console
$ sudo systemctl enable --now lindeskd                    # the broker (system)
$ systemctl --user enable --now lindesk-session           # your session agent
```

On GNOME, enable the extension that reports focus changes, then log out and in:

```console
$ gnome-extensions enable lindesk@lindesk.org
```

On KDE, enable the **lindesk** KWin script (System Settings → Window Management → KWin
Scripts). COSMIC and X11 need nothing extra: their adapters are built into
`lindesk-session`.

## Check it

```console
$ lindeskctl doctor       # what the machine supports, and whether every piece is running
$ lindeskctl status       # what lindesk is doing right now
$ lindeskctl watch        # the same, live
$ lindeskctl profile list # which profile was picked for this machine, and why
```

Optional, once the machine is idle: `lindeskctl calibrate` measures its latency baseline
(≈15 s) so lindesk scales I/O throttles to the real disk instead of nominal values (see
[Hardware awareness](hardware.md)).

## AI agents

The packages install `lindesk-mcp`, an MCP server for local agents. Claude Code starts it
over stdio, no service needed:

```console
$ claude mcp add lindesk -- lindesk-mcp
$ lindeskctl mcp config --client claude-desktop   # or cursor, generic
```

For clients that connect to a running endpoint, enable the (not enabled by default) user
socket: `systemctl --user enable --now lindesk-mcp.socket`. See [MCP](mcp.md).

## What gets installed

Besides the binaries (`lindeskd`, `lindesk-session`, `lindeskctl`, `lindesk-bench`,
`lindesk-mcp`; with telemetry also `lindesk-data` and
`/usr/lib/lindesk/lindesk-telemetry-sink`) and their units: the shipped profiles in
`/usr/share/lindesk/profiles.d/` (yours go in `/etc/lindesk/profiles.d/` or
`~/.config/lindesk/profiles.d/`), the change history in `/var/lib/lindesk/changes/`
(created by systemd-tmpfiles), man pages for every command (`man lindeskctl-changes`,
`man lindesk-mcp`) and shell completions.

## Shell completions by hand

```console
$ lindeskctl completions bash > ~/.local/share/bash-completion/completions/lindeskctl
$ lindeskctl completions zsh  > ~/.zfunc/_lindeskctl
$ lindeskctl completions fish > ~/.config/fish/completions/lindeskctl.fish
```

`elvish` and `powershell` work too.

## Requirements and preflight checks

lindesk needs Linux with `/proc` and a kernel ≥ 3.10 to run at all. Everything else only
changes how much it can do:

| Missing | Effect |
|---|---|
| kernel ≥ 4.20 (PSI) | no stall feedback: static class weights only |
| kernel ≥ 5.4 | no cgroup uclamp: boosts use weights only |
| cgroup v2 | CPU weights only, no I/O control |
| PSI enabled (`psi=1` if the kernel has `CONFIG_PSI_DEFAULT_DISABLED`) | as without PSI |
| systemd | the raw cgroup backend instead of unit properties |
| polkit | only root can change classes |
| D-Bus system bus | `lindeskd` fails to start unless run with `--no-dbus` |
| a conflicting daemon (system76-scheduler, ananicy(-cpp), uresourced) | both fight over priorities: `install.sh` offers to disable it (a revertible change; `--disable-conflicts` / `--keep-conflicts`), packages print the command (`sudo lindeskctl setup conflicts --disable`). See [Other priority daemons](conflicts.md) |

`install.sh` checks these before it builds or installs anything, and also checks the Rust
toolchain against the workspace MSRV when it builds:

```console
$ ./packaging/install.sh --preflight        # only check, as any user
$ sudo ./packaging/install.sh --skip-preflight   # install without checking
```

A failure (not Linux, no `/proc`, kernel < 3.10, `cargo`/`rustc` missing or too old) stops
the install; everything else is a warning. After installing onto the live system it runs
`lindeskctl doctor --preflight`, the daemons' own start-up checks. If those fail, lindesk is
installed but its services are **not** enabled or started; the installer prints what failed
and the commands to enable the services once it is fixed.

Run as a regular user, `./packaging/install.sh` checks and builds as you, then asks for
`sudo` for the install step. On success it enables and starts `lindeskd`, enables
`lindesk-session` for every user, and starts it right away in every graphical session that
is already open (through `loginctl` and each user's systemd manager), so nobody needs to
log out. It ends with what to do next: `lindeskctl` (status), `lindeskctl watch` (live),
and how to enable the GNOME extension should `lindesk-session` not manage to enable it
itself on first start. The packages do the same, best effort.

The `.deb`, `.rpm` and Arch packages run `lindeskctl doctor --preflight --quiet` after
installing. A failure never fails the package transaction: it prints a warning, and
`lindeskd` is installed (and enabled where the distribution does that) but not started.

The daemons run the same checks every time they start and exit with status 78 (`EX_CONFIG`)
when a hard requirement fails, so `systemctl status lindeskd` shows the reason. See
[doctor](doctor.md#requirements) for the full list of checks.
